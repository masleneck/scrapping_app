# Исследовательский раздел: real-source scraping для УМС

## 1. Цель экспериментов
Проверить, может ли резервный канал веб-скрейпинга поддерживать актуальность расписания рейсов при сбоях основного прокси-сервиса, и оценить качество событийной модели `RMSEVENT_ADD/UPDATE/DELETE`.

## 2. Источники данных
- Официальный источник: `https://www.svo.aero/bitrix/timetable/`.
- Агрегаторы: `kupibilet`, `yandex rasp`, `trip.com`.

## 3. Методика
- Сбор данных выполняется периодически (scheduler) и по запросу (`GET /flights/scrape-real`).
- Для каждого рейса строится стабильный ключ (`source + flight_number + direction + scheduled_time`).
- Текущее состояние сравнивается с сохраненным состоянием (`real_source_state`):
  - новый ключ -> `RMSEVENT_ADD`;
  - ключ есть, но payload изменился -> `RMSEVENT_UPDATE`;
  - ключ исчез при успешном чтении источника -> `RMSEVENT_DELETE`.
- Статусы чтения источников (`ok/empty/blocked/error`) сохраняются в `real_source_runs`.

## 4. Метрики
- Надежность канала:
  - `sources_ok`, `sources_blocked`, `sources_error` на запуск.
- Полезная событийность:
  - `add`, `upd`, `del`, `unchanged`.
- Динамика источников:
  - временные ряды по `status` и по `add/upd/del`.
- Актуальное покрытие:
  - количество активных рейсов по статусам (`active_by_status`).

## 5. Протокол эксперимента
1. Поднять стек (`make up`), применить миграции (`alembic upgrade head`).
2. Запустить серию сборов (планировщик + ручной запуск).
3. Снять агрегаты:
   - `GET /events/real-stats?hours=24`;
   - `GET /events?event_type=RMSEVENT_ADD` (и аналогично для update/delete).
4. Сопоставить успешные и проблемные источники по временным интервалам.

## 6. Результаты (первичный прогон, 1 марта 2026)
- `svo_official`: `ok`, ~2617 snapshot.
- `kupibilet_aggregator`: `ok`, ~39 snapshot.
- `yandex_rasp_aggregator`: `blocked` (captcha/challenge).
- `tripcom_aggregator`: `blocked/empty` (challenge page).

Вывод: официальный источник обеспечивает основной объем данных, агрегаторы частично дополняют, но чувствительны к anti-bot механизмам.

## 7. Правовые и технические ограничения
- В реализации **не применяется обход CAPTCHA**.
- Используются только легальные механизмы устойчивости:
  - retry/backoff,
  - стандартные HTTP-заголовки,
  - диагностическое логирование blocked/error.
- При `blocked/error` источник помечается как недоступный, а не «ломается» обходом защит.

## 8. Интерпретация для УМС
- Наличие резервного real-source канала снижает риск простоя обновлений.
- Дедупликация по состоянию уменьшает шум и позволяет хранить значимые изменения.
- Аналитика по источникам показывает, какой канал надежен в конкретный период и где нужна операционная замена/приоритизация источника.
